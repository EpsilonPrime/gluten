# GenerateRel: Proposal for Upstreaming to Substrait

**Status:** Draft - Ready for Substrait Community Discussion
**Priority:** HIGH - Critical Spark/SQL feature without Substrait equivalent
**Estimated Effort:** 2-4 weeks (proposal + implementation)

---

## Executive Summary

**GenerateRel** is a table-generating relational operator that expands a single input row into multiple output rows based on a generator expression. This is essential for SQL operations like:
- `EXPLODE` / `POSEXPLODE` (Spark)
- `UNNEST` (PostgreSQL, Presto, DuckDB)
- `LATERAL VIEW` (Hive)
- Array/Map expansion operations

**Current Status:**
- ❌ Does NOT exist in official Substrait v0.77.0
- ✅ Implemented in Gluten as custom extension
- ❌ No active Substrait proposal or discussion found (as of 2025-12-12)
- ✅ Strong candidate for upstreaming

---

## The Problem

### What is a Table-Generating Function?

Table-generating functions take a **single input row** and produce **0 or more output rows**:

```sql
-- Input: 1 row with array [1, 2, 3]
SELECT id, value FROM table
LATERAL VIEW EXPLODE(array_col) AS value;

-- Output: 3 rows
-- id=1, value=1
-- id=1, value=2
-- id=1, value=3
```

### Why ExpandRel Doesn't Solve This

Substrait has `ExpandRel`, but it's designed for **fixed-cardinality expansion** (e.g., GROUP BY CUBE where every input row produces exactly N output rows).

GenerateRel needs **variable cardinality**:
- Array of 3 elements → 3 rows
- Array of 0 elements → 0 rows (or 1 row with NULL if `outer=true`)
- Map with 5 entries → 5 rows

## Gluten's Current Implementation

### Proto Definition

```proto
message GenerateRel {
  RelCommon common = 1;
  Rel input = 2;

  // The generator expression (e.g., explode(array_col))
  Expression generator = 3;

  // Columns from input to include in output
  repeated Expression child_output = 4;

  // If true, generate at least one row even if generator returns empty
  // Similar to LEFT OUTER JOIN semantics
  bool outer = 5;

  substrait.extensions.AdvancedExtension advanced_extension = 10;
}
```

### Field Descriptions

**generator (Expression):**
- The table-generating function to apply
- Must be a function that returns a list/array/map type
- Examples: `explode(array_col)`, `posexplode(array_col)`, `unnest(array_col)`

**child_output (repeated Expression):**
- Expressions from the input row to include in output
- Typically field references to pass through input columns
- Output schema = child_output + generator output columns

**outer (bool):**
- `false` (default): If generator returns empty, produce 0 rows
- `true`: If generator returns empty, produce 1 row with NULL for generator columns
- Corresponds to `LATERAL VIEW OUTER` in Spark/Hive

### Usage in Gluten

**Spark SQL:**
```sql
SELECT id, name, skill
FROM employees
LATERAL VIEW EXPLODE(skills) AS skill;
```

**Translates to:**
```
GenerateRel {
  input: ReadRel(employees)
  generator: explode(field_reference(skills))
  child_output: [field_reference(id), field_reference(name)]
  outer: false
}
```

**Backend Support:**
- **ClickHouse**: Translates to `ARRAY JOIN`
- **Velox**: Native UNNEST support

## Comparison with Other Systems

| System | Operator/Function | Syntax |
|--------|------------------|--------|
| Spark | LATERAL VIEW EXPLODE | `LATERAL VIEW EXPLODE(arr) AS x` |
| Hive | LATERAL VIEW | `LATERAL VIEW EXPLODE(arr) AS x` |
| PostgreSQL | UNNEST | `UNNEST(arr) AS x` |
| Presto/Trino | UNNEST | `CROSS JOIN UNNEST(arr) AS x` |
| DuckDB | UNNEST | `UNNEST(arr)` |
| ClickHouse | ARRAY JOIN | `ARRAY JOIN arr AS x` |
| BigQuery | UNNEST | `UNNEST(arr) AS x` |

**Commonality:** All major SQL engines have this feature with slightly different syntax but identical semantics.

## Proposed Changes for Substrait

### 1. Add GenerateRel to algebra.proto

Insert after ExpandRel definition:

```proto
// Generates zero or more output rows for each input row by applying
// a table-generating function (also known as unnest, explode, or lateral view).
//
// The generator expression must evaluate to a collection type (list or map).
// For each element in the collection, one output row is produced containing:
// - All fields specified in child_output (passed through from input)
// - Fields generated by the generator function
//
// Example:
//   Input: {id: 1, skills: ["Java", "Python"]}
//   Generator: explode(skills) AS skill
//   child_output: [id]
//
//   Output:
//     {id: 1, skill: "Java"}
//     {id: 1, skill: "Python"}
message GenerateRel {
  RelCommon common = 1;

  // The input relation
  Rel input = 2;

  // The table-generating function expression.
  // Must evaluate to a collection type (list, map, or struct).
  // The function determines how many rows are generated per input row.
  Expression generator = 3;

  // Expressions from the input to include in the output.
  // These are evaluated once per input row and replicated across
  // all generated rows for that input.
  repeated Expression child_output = 4;

  // If true, generate at least one row even if the generator returns empty.
  // The generated columns will be NULL in this case.
  // Corresponds to LEFT OUTER semantics.
  bool outer = 5;

  substrait.extensions.AdvancedExtension advanced_extension = 10;
}
```

### 2. Add to Rel union

In the `Rel` message:

```proto
message Rel {
  oneof rel_type {
    // ... existing relations ...
    ExpandRel expand = 15;
    GenerateRel generate = 16;  // ADD THIS
    // ... other relations ...
  }
}
```

### 3. Document Common Generator Functions

Recommend standard function signatures in function extensions:

```yaml
# Explode array into rows
- name: explode
  signature: list<T> -> T
  description: Generates one row per array element

# Explode array with position
- name: posexplode
  signature: list<T> -> struct{pos: i64, val: T}
  description: Generates one row per array element with position index

# Explode map into key-value rows
- name: explode_map
  signature: map<K,V> -> struct{key: K, value: V}
  description: Generates one row per map entry

# Unnest (generic)
- name: unnest
  signature: list<T> -> T
  description: Alias for explode, common in PostgreSQL/Presto
```

## Risks and Mitigations

### Risk 1: Community Pushback on Complexity
**Mitigation:**
- Demonstrate widespread use across SQL engines
- Show that ExpandRel doesn't solve this use case
- Provide clear semantics and examples

### Risk 2: Disagreement on Generator Expression Representation
**Mitigation:**
- Open to alternative designs (e.g., function reference vs full expression)
- Willing to iterate based on feedback
- Can start with minimal design and extend later

### Risk 3: Overlap with Future Features
**Mitigation:**
- Check if any in-flight proposals address this
- Design to be composable with other operators
- Use AdvancedExtension for extensions

Table-generating functions are essential for:
